# 0.5.0 — Sync support (page size, archived contacts, raw payloads, quota, resumability, tracking categories)

## Context

0.3.0 taught the list endpoints to query and page; 0.4.0 added module-level
throttle configuration. Both were built against org-level, single-call
endpoints — `organisation`, `users`, `branding_themes`, `connections`. Those
proved the client, the throttle and the error mapping, but they never
exercised a large paged extract.

Statey's Xero migration is now blocked on the parts that only show up at that
scale. Its legacy `lib/xero_api/` encodes six years of production lessons —
`pageSize=1000`, `includeArchived=true`, a resume log, an early stop when the
daily quota runs low — and the rule for the port is that where the equivalent
doesn't exist here, it gets built here rather than worked around in the app.
This release is that set of gaps.

Shipping as **0.5.0**. Breaking, because the class currently named
`TrackingCategory` is being renamed to `Tracking` (see section 6).

Seven items were identified. Six are in scope below. The seventh — passing
`logger:` to the throttle so fail-open warnings reach `Rails.logger` instead
of `Kernel.warn` — needs no gem change: `RedisTokenBucket#initialize` has
accepted `logger:` since 0.2.0. It is a one-line fix in the host app's
initializer, noted here only so it doesn't get lost.

## Decisions locked in

- **Page size:** a client-level default (`Client.new(page_size: 1000)`) with a
  per-call override on every list method. Callers who set neither keep Xero's
  default of 100, so nothing changes underneath existing users. A host app
  configures it once next to the throttle, and no individual extract can
  forget it and quietly cost 10x the API calls.
- **Raw payloads:** `Resource#raw` returning the untouched response hash,
  opt-in per client via `Client.new(retain_raw: true)`. Off by default — a
  1,000-invoice page roughly doubles in memory when every resource holds its
  source hash, and that lands during exactly the full syncs this is for.
  Populated on resources built directly from a response, not on nested
  objects (see section 3).
- **Quota introspection:** `client.rate_limit(tenant_id)` returning a
  `XeroKiwi::RateLimit`. It blends two sources and reports **the stricter of
  the two**: what Xero's response headers last reported, and what the
  configured throttle bucket has left. A configured limit is a ceiling we
  never exceed; a reported limit is reality we can't argue with.
- **Resumability:** page-level `each_<resource>_page` helpers yielding a
  `Page`, plus `start_page:` on both those and the existing item-level
  `each_<resource>` helpers. No response caching — see "Rejected" below.
- **Tracking categories:** two classes. The nested assignment shape is
  renamed `Tracking` (Xero's own field name for it); `TrackingCategory`
  becomes the `/TrackingCategories` endpoint resource, with a new
  `TrackingOption` for its `Options` array.
- **Archived contacts:** `include_archived:` on `contacts` only. It is a
  distinct query parameter, not a `where` filter — filtering on
  `contact_status` returns *only* archived contacts, where the point is to
  get both in one pass.

## Rejected

- **Caching response bodies in the gem**, as a way to make a sync resumable.
  Rejected on arithmetic. A Xero invoice with line items is roughly 1–3 KB of
  JSON; at `pageSize=1000` that's 1–3 MB per page, so a 50,000-invoice tenant
  is 50–150 MB for invoices alone, before contacts, credit notes,
  prepayments, overpayments and payments. It is also less correct than a
  cursor: a cached body gets re-imported as though fresh, and it raises
  invalidation questions (has the tenant written since?) that skipping a
  page whose rows are already stored never has to answer. The resumable unit
  is an integer — a page number — which is what section 5 exposes.
- **Making `page_size` default to 1000 gem-wide.** It would match the legacy
  app everywhere with no configuration, but it changes response sizes and
  memory for every existing caller without them asking — too much to bury in
  a minor release.
- **Hanging the rate-limit blend off `Page`.** The blended number isn't a
  property of any one response, and it would be nil on single-resource
  returns unless duplicated there too. It lives on the client.

## Design

### 1. `page_size`

Xero's `pageSize` query param, on the paged list endpoints.

```ruby
client = XeroKiwi::Client.new(access_token: "...", page_size: 1000)

client.invoices(tid)                   # pageSize=1000 — the client default
client.invoices(tid, page_size: 100)   # per-call override
```

- `Client#initialize` gains `page_size: nil`, stored as `@page_size`.
- `list_request` resolves `page_size || @page_size` and, when non-nil, sets
  `params["pageSize"]`. Nil means the param is omitted entirely and Xero
  applies its own default, which is today's behaviour.
- Thread it through `walk_pages` and every `each_*` helper. Without that,
  `invoices(page_size: 1000)` would page at 1000 while `each_invoice` still
  paged at 100 — a difference nobody would expect and nothing would catch.

**Termination.** `walk_pages` currently stops on `pg.size < pg.page_size`,
where `build_page` falls back to `items.size` when Xero returns no
`pagination` envelope. That fallback makes the comparison trivially false
(`items.size < items.size`), so the early break never fires and the walk can
only end on a fully empty page — one wasted request per walk.

Fix it by comparing against the largest page **observed so far in this walk**,
tracked locally in `walk_pages`:

```ruby
break if largest_seen && pg.size < largest_seen
```

Do **not** compare against the requested `page_size`. Xero clamps a request
above an endpoint's maximum, so asking for 2000 on an endpoint capped at 1000
would make page 1 look short (`1000 < 2000`) and end the walk after a single
page — silently truncating the sync. One wasted request is a much better
failure than lost rows. The largest-observed value is safe because it is
measured rather than assumed: pages of 1000, 1000, 500 break correctly on the
500 whatever was asked for.

This can't avoid the extra request when the entire result fits in one page —
nothing has been observed to compare against. That case needs Xero's own
default, which the gem shouldn't hardcode.

### 2. `include_archived`

```ruby
client.contacts(tid, include_archived: true)
client.each_contact(tid, include_archived: true, modified_since: t) { |c| ... }
```

Contacts only. `list_request` gains an `extra_params:` hash so the
contacts-specific parameter doesn't leak onto the generic path that eight
other resources share.

This matters beyond contacts themselves: without it, archived contacts vanish
locally, and a contact-groups extract can't tell which of its members are
archived — Xero keeps serving archived contacts as group members.

### 3. `Resource#raw`

```ruby
client = XeroKiwi::Client.new(access_token: "...", retain_raw: true)
contact = client.contact(tid, id)

contact.raw            # => {"ContactID" => "...", "ContactPersons" => [...], ...}
contact.raw["Foo"]     # anything Xero returns that the gem doesn't model
```

Today `Resource#initialize` hydrates the modelled attributes and drops
`attrs`, and `#to_h` rebuilds a snake_case hash from those attributes. So the
original payload is unrecoverable, and `#to_h` is a *projection* — different
keys, different nesting. Anything storing `#to_h` where it used to store the
response body will find its readers return nil rather than raise.

- `Client#initialize` gains `retain_raw: false`, stored as `@retain_raw`.
- `Resource::ClassMethods#from_response(payload, retain_raw: false)` passes
  the flag into each `new`.
- `Resource#initialize` stores `@raw = attrs.freeze` when the flag is set,
  `nil` otherwise. `#raw` reads it.

**Top-level only.** Nested objects (line items, addresses, contact persons)
don't carry `#raw`. The top-level resource's raw hash already contains every
nested payload verbatim, so `contact.raw["ContactPersons"]` gets there
without threading the flag through `Hydrator` and every `build_object` call.
Document the boundary; don't blur it.

### 4. `client.rate_limit(tenant_id)`

```ruby
rl = client.rate_limit(tid)

rl.day_remaining        # => 500     the binding number
rl.minute_remaining     # => 55
rl.day_below?(1000)     # => true
rl.minute_below?(10)    # => false
rl.day_source           # => :configured | :reported | nil
rl.minute_source        # => :configured | :reported | nil
rl.known?               # => true
rl.reported             # => #<RateLimit::Reported day: 3000, minute: 58>  or nil
rl.configured           # => #<RateLimit::Configured day: 500, minute: 55>  or nil
```

(Sketched as a single `binding_source` during planning; split per window on
implementation, because one reader covering both the day and minute figures
can't say which of the two it's describing.)

`day_remaining` is `[reported&.day, configured&.day].compact.min`. If Xero
reports 3,000 left but a bucket configured at 4,900/day has 500 tokens, we
honour 500. If another application on the same tenant has burned the quota so
Xero reports 50 while our bucket still shows 2,000, we honour 50.

**Reported** — a Faraday response middleware reads `X-DayLimit-Remaining` and
`X-MinLimit-Remaining` off every response and stores them per tenant on the
client, behind a mutex. It's as fresh as the last call to that tenant and nil
before the first one.

**Configured** — a new read-only `RedisTokenBucket#remaining(key)` that runs
the same refill arithmetic as `acquire` but commits no decrement, returning
current minute and day token counts. Add `#remaining` to the limiter contract
as **optional**: `NullLimiter` returns nil, and the client checks
`respond_to?(:remaining)` so a custom limiter written against the 0.2.0
contract keeps working.

**No information.** When neither source has data, `day_remaining` is nil and
`day_below?` returns false. Not knowing how much quota is left is not a
reason to halt a sync, and halting would break the common case — a loop
whose first call is what populates `reported`.

### 5. Page-level iteration and `start_page:`

```ruby
client.each_invoice_page(tid, start_page: 8, modified_since: t) do |page|
  upsert(page.to_a)
  cursor.advance(:invoices, page.page)   # same transaction as the upsert
end
```

`walk_pages` is private and the `each_*` helpers yield items, so the page
number never reaches the caller — which is the one thing a resumable sync
needs to record. `Page` already carries `page`; it just isn't surfaced.

- Add `each_<resource>_page` for all nine list resources, yielding `Page`.
- Add `start_page:` (default 1) to those and to the item-level `each_*`.
- Refactor `walk_pages` to take `start_page:` and yield whole pages; the
  item-level helpers become a thin `pg.each` over it.
- Both return an `Enumerator` when called without a block, matching the
  existing helpers.

Recording `page.page` in the same transaction as the upsert is what makes the
marker unable to outlive the data it stands for. A resume marker written when
the HTTP response lands — before the rows are stored — can survive a crash
that the rows don't, and the next run then skips a page it never imported.

### 6. Tracking categories

Xero uses one name for two objects. The gem currently models only the first.

**The assignment**, nested in a line item or a contact:

```json
{ "TrackingCategoryID": "abc", "TrackingOptionID": "def",
  "Name": "Region", "Option": "Eastside" }
```

**The definition**, from `GET /TrackingCategories`:

```json
{ "TrackingCategoryID": "abc", "Name": "Region", "Status": "ACTIVE",
  "Options": [ { "TrackingOptionID": "def", "Name": "Eastside",
                 "Status": "ACTIVE" } ] }
```

They share a name and one ID field and diverge after that. One class serving
both would leave each shape carrying fields that are structurally always
empty, with no way for a caller to tell which kind they hold.

- **`Accounting::Tracking`** — the current `TrackingCategory`, renamed.
  `Tracking` is Xero's own field name for it on a line item.
- **`Accounting::TrackingCategory`** — the endpoint resource.
  `payload_key "TrackingCategories"`, `identity :tracking_category_id`,
  attributes `tracking_category_id`, `name`, `status`, and `options` as a
  collection of `TrackingOption`.
- **`Accounting::TrackingOption`** — `tracking_option_id`, `name`, `status`.
- `client.tracking_categories(tid)`, `client.tracking_category(tid, id)`,
  `client.each_tracking_category(tid)`.
- Update the three existing references — `LineItem#tracking` and Contact's
  `sales_tracking_categories` / `purchases_tracking_categories` — to point
  at `Tracking`.

The endpoint isn't paged. `each_tracking_category` still works (the walk ends
on the first short page) and exists so all ten list resources behave
consistently, but there's no reason to reach for it over the plain list call.

**Open — verify before shipping.** Xero documents Contact's
`SalesTrackingCategories` / `PurchasesTrackingCategories` as
`{TrackingCategoryName, TrackingOptionName}`, which is neither of the two
shapes above. Today those map to the assignment class, which would leave all
four of its attributes nil. Contact also declares flat
`tracking_category_name` / `tracking_option_name` attributes alongside them,
which suggests the confusion predates this release. This release keeps those
two collections pointing at the renamed class — a pure rename, no behaviour
change — and the mismatch gets confirmed against a real payload and fixed
separately, rather than being guessed at here.

## Out of scope

- **Writers.** Reader-only, as in every release so far.
- **The `logger:` wiring**, which is a host-app initializer change, not a gem
  change.
- **Fixing Contact's tracking collections**, pending a real payload.

## Testing

- `page_size` — client default applied, per-call override wins, param omitted
  when neither is set, and threaded into `each_*` and `each_*_page`.
- Walk termination — a short final page ends the walk without an extra
  request; a single-page result still ends on the empty page; and, the one
  that matters, a walk whose requested size was clamped by Xero (ask 2000,
  receive 1000) runs to completion instead of stopping after page 1.
- `include_archived` — present on contacts, rejected as an unknown kwarg
  elsewhere.
- `#raw` — populated when opted in, nil when not, frozen, preserves keys the
  gem doesn't model, and absent on nested objects.
- `rate_limit` — reported-only, configured-only, both (asserting the min is
  taken in each direction), neither, `binding_source`, and a limiter that
  doesn't implement `#remaining`.
- `start_page:` — starts where asked, page numbers reach the block in order,
  Enumerator when blockless.
- Tracking — the renamed class still hydrates a line item, the endpoint
  resource hydrates nested options, and the client methods hit the right path.
- `RedisTokenBucket#remaining` — against a real Redis, asserting it commits
  no decrement (the `:redis` tag; these are excluded when none is reachable).

**Cassettes.** The throttle and quota work is the first thing here whose
correctness depends on response *headers* rather than bodies, and there are
no VCR cassettes for any Kiwi request yet. Worth recording a small set
against the demo org as part of this release — a request shape nothing
exercises is how a reference to a deleted class survives in a live pipeline.

## Notes for the host app

Not gem work, but this release is what unblocks it, and each of these is a
silent behaviour change rather than an error:

- `#to_h` is not the Xero payload. Anywhere the legacy code stored
  `response.body`, storing `#to_h` changes both the keys (snake_case) and the
  nesting (no `{Organisations: {Organisation: ...}}` envelope). Readers
  return nil; nothing raises.
- Pass `logger:` to the throttle, or fail-open Redis warnings go to
  `Kernel.warn` and are invisible in production.
- `Throttle::DailyLimitExhausted` carries `retry_after` in seconds and is
  meant to re-enqueue a job, not sleep for hours. Something has to catch it.
- A reliable `error_code` changes downstream behaviour wherever the legacy
  code scraped a status out of an exception message and usually got nil.
